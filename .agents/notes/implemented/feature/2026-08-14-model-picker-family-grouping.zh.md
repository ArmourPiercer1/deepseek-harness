# Agent Note: 模型选择器中的系列分组与全选

Status: implemented

[English](2026-08-14-model-picker-family-grouping.md) | 中文

## 问题

[Models 页声明流程](2026-08-04-declaring-a-provider-from-the-models-page.md)的获取模型选择器把提供方发现的模型渲染成一条无差别复选框列表。这对厂商自家的几个模型是合适的形态，对这个流程存在的初衷却是错的：中转站或网关一次就提供全部厂商的目录，上百个 id 滚动起来像一堵墙，而且没有批量选中或清空的途径——只想从中转站挑三个模型的用户，要么逐个取消勾选选择器预选的那九十七个，要么把它们全部配置进去。

## 决策

选择器按 **ID 所点名的系列** 对候选分组，并为整个列表增加一个**全选**开关。

系列是 id 的前导标识 token：`claude-3-5-sonnet` 与 `claude-3-opus` 同属 `claude`，`gpt-4o` 是 `gpt`，`gemini-2.0-flash` 是 `gemini`，`deepseek-chat` 是 `deepseek`。带厂商限定的 id（`openai/gpt-4o`）按斜杠之后的部分归类，那才是命名系列的部分。推导就是这条规则的全部——`src/client/modelGrouping.ts` 中的 `modelFamily`——因此它无需任何厂商表即可保持不过时：来自本构建从未听说过的提供方的模型，也仍会落进一个读起来像其系列的组。各组按首次出现顺序渲染，组内 id 保持发现顺序，上方是点名系列及其数量的标题（`Claude · 2`）。显示大小写来自一张小表，只收录日常拼写并非普通首字母大写的那几个系列（`gpt` → `GPT`、`deepseek` → `DeepSeek`、`o1` → `o1`）；其余一律回退为首字母大写。

开关位于滚动区上方，选中全部不同的候选 id——即采纳实际写入的单元——而一旦全部选中，它就读作自己的反义并清空列表。已配置过的候选与其它行一样参与开关，但采纳时仍保留被用户调整过的行、而非重新发现的那份，因此「全选」绝不会覆盖用户已更正的容量。分组只是呈现：采纳仍按发现顺序把 profile 的 `models` 数组写回，保持不变。

## 备选方案

- **维护一张厂商表**（`claude-*`、`gemini-*`、`gpt-*`…）来驱动分组。不予采纳：每来一个新厂商都要先加一行，其模型才能合理分组，且表可能与中转站实际返回的 id 产生漂移。前导 token 启发式无需任何知识，也永远不会过时。
- **在每个系列标题旁放一个组内全选开关。** 本次不予采纳：需求是一个全局开关，而一个系列的行数不多，全局开关加逐行复选框已覆盖批量场景。若全局开关被证明过粗，组内开关是自然的后续。
- **固定「全选」、永远只做选中。** 不予采纳：全部选中后用户需要的是反义操作，因此控件在全选时把标签翻转为「取消全选」，而不是假装一次无效点击就是进展。

## 后果

中转站的列表现在看起来就像它实际包含的那些系列，只想用几个模型的用户不必先取消其余所有勾选，也不必全部采纳。启发式可能把一个人类眼中的同一系列拆开（`qwen-max` 与 `qwen2.5-72b` 落在不同组），这透明且无害，因为每个标题下的 id 仍然可见。选择器只多了一行工具栏和一个滚动容器；获取选择器既有的默认勾选、采纳保留已调整行与取消语义均保持不变。

## 测试

`tests/model-grouping.client.spec.ts` 固定纯函数契约：系列推导（普通、带厂商限定、大小写、空白）、大小写表及其回退、按首次出现的组顺序、组内发现顺序、随组携带的元数据以及空列表。`tests/provider-form.client.spec.tsx` 用脚本化 wire face 驱动渲染后的对话框：带数量的分组标题、采纳按发现顺序写回，以及开关对整个列表的选中、清空与再选中，且调整过的行在采纳后仍然存活。`apps/web/tests/models-settings.e2e.ts` 通过对本地 mock 端点的真实询问驱动装配后的选择器，并以 ARIA golden 固定分组后的对话框。
