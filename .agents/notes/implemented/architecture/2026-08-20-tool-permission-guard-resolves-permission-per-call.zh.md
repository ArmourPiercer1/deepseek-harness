# Agent Note: The tool permission guard resolves `ctx.permission` per tool call

[English](2026-08-20-tool-permission-guard-resolves-permission-per-call.md) | 中文

Status: implemented

## 问题

守卫是一个 `tools/pre-execute` 监听器，消费引擎行发布的 `permission` 服务，两行位于同一个 cordis.yml 中。Loader 并行激活各行，因此守卫的 `apply()` 可能在引擎行注册服务之前运行。apply 时的服务读取与该顺序存在竞争：严格 `ctx.get` 只返回提供方 fiber 已激活的服务，读取早于提供方激活就使守卫不注册任何东西——组合进来的 deny 规则在整个会话期间静默失效。另一方面，引擎解析器拒绝（格式错误）或忽略（主内容字段上的 `param:value`）的规则会被 `compile` 丢弃，而守卫没有任何路径上报这一事实，被丢弃的 deny 完全不可见。

## 决定

守卫在 `tools/pre-execute` 监听器内按每次工具调用解析 `ctx.permission`，而非在 `apply()` 时。每次调用都用严格 `ctx.get` 读取服务，并在服务出现后的首次调用上惰性编译该 scope 的规则一次。服务缺失时——该 scope 未组合引擎行——守卫通过 `next()` 委托，调用不受守卫地继续：守卫的"松散置于组合中"语义成立，并且一旦引擎行激活，它就在任意激活顺序下自行武装。

在那次首次编译时，守卫通过自己的日志器记录引擎解析器报告的每条诊断：携带引擎 `error:` 前缀的诊断以 error 级别记录，其余以 warn 级别记录。`permission/decision` 审计追加与决策到 pre-execute 的映射保持不变。

## 已考虑的替代方案

**apply 时解析加硬 `inject: ['permission']`**——团队插件采用的方式。注入使 fiber 等待服务出现并消除竞争，但也使守卫在没有引擎行时无法组合：组合了守卫却没有引擎的 scope 会激活失败。权限 seam note 为团队插件指定硬依赖，因为其审批路径必须依赖它；守卫保留松散契约，以便放入任何已带引擎的组合。

**等待或重试直到服务出现**——轮询或就绪事件会给一个应当保持薄消费者的监听器加上定时器与额外状态；按调用解析无需这些就获得同样的顺序无关性，因为调用正是守卫需要服务的时刻。

**服务缺失时失败关闭**——拒绝每次调用在最坏情况下更安全，但它会把"未组合引擎行"这一有文档的松散状态变成把 agent 锁在所有工具之外的配置错误。缺失依然是保持 scope 不受守卫的有文档方式。

## 后果

- 顺序无关：守卫在任意行激活顺序下都正确。单元测试先挂载守卫再挂载引擎，断言匹配调用在引擎出现前被允许、出现后被拒绝。
- 首次被评估的调用承担规则编译与诊断日志的开销；后续调用复用已编译的策略。
- 被丢弃的 deny 在首次使用时可见于该 scope 的日志流。级别映射使守卫耦合到引擎的诊断前缀——这是同一家族包内部的契约，前缀格式归引擎的 `compile` 契约所有。
- 松散语义是承重墙：只带守卫行而不带引擎行的组合会不受守卫地运行工具，组合测试断言这一状态而非报错。
