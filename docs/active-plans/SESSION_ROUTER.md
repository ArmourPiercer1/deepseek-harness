# SESSION_ROUTER — Team vNext 无人值守开发：路由与门禁要求

**文档状态**：执行路由协议 / 对当前会话主代理与其拉起的全部子代理有约束力
**适用任务**：Agent Team vNext 无人值守长开发任务
**日期**：2026-08-29

> 本文档是把 vNext 开发计划作为**无人值守长任务**运行的路由与门禁协议。
> 它只规定四件事：**谁执行、允许尝试几次、门禁如何验收、状态如何流转**。
> 它不修改上游文档对语义、兼容性、UI、开发顺序的任何要求：
>
> 1. `DSH_Agent_Team_vNext_Architecture_Baseline_20260827.md`
> 2. `DSH_Agent_Team_vNext_Compatibility_Design_20260828.md`
> 3. `DSH_Agent_Team_vNext_UI_Interaction_Design_20260828.md`
> 4. `DSH_Agent_Team_vNext_Development_Plan_20260828.md`
>
> 本文档与上游文档冲突时，**上游文档优先**，冲突必须记入执行日志（§7）并报告用户。

---

# 1. 模型路由

1. **所有工作由 `qiyuan-self/qwen3.8-27b` 完成**。包括：
   - 全部开发任务（开发计划中的 T-x.x）；
   - 全部审查验收（每 Gate 的 3 个独立审查子代理）；
   - 实质性补充与文档性补充；
   - 补充后的对抗式重审；
   - characterization tests、invariant test helpers 等一切辅助工作。
2. 不混用其他模型。开发计划 §1 的角色分派（Architect / Senior executor / Fast executor / Reviewer）只描述任务的难度与能力要求，所有角色由同一模型承担。
3. 主代理自身运行在 `qiyuan-self/qwen3.8-27b` 上；其拉起的审查子代理与其他工作子代理继承主代理的模型路由。
4. **路由核验**：执行启动时，主代理必须核验当前会话的模型路由确为 `qiyuan-self/qwen3.8-27b` 并记录核验证据到执行日志；不满足时停止执行并报告用户，不得开始。

---

# 2. 开发任务执行上限

1. 每个开发任务（T-x.x）**允许重试两次，即最多执行三次**（1 次初次 + 2 次重试）。
2. 执行次数按任务在执行日志（§7）中单独记录，不跨任务结转或共享。
3. 一个任务三次执行后仍未完成或自验未通过时：
   - 若阻塞是**局部的**（只影响该任务内部实现，不改变门禁级语义或用户可观察语义），主代理可跳过该任务并记录证据、标记 TODO，继续同阶段后续任务；TODO 必须在阶段 Gate 审查前关闭，或在 Gate 报告中显式声明并记入执行日志；
   - 若阻塞**涉及 Gate 出口判据或任何用户可观察语义**，状态转为**阻塞**（§5）。

---

# 3. 门禁审查与验收

## 3.1 审查组成

1. 每个 Gate（G0–G12）的审查由 **3 个独立审查子代理**执行。
2. 独立性要求：
   - 3 个新拉起的子代理，无会话继承、互不可见；
   - 每个审查 brief 只包含：该 Gate 的定义与出口判据、4 份上游文档的相应章节、受审的 commit 区间（base → head）与复现方式、以及“独立核实证据并给出裁决”的指令；
   - 主代理不得向任何审查者转述其他审查者的意见、自己的判断或任何期望结论；
   - 每个审查者必须独立阅读代码 / diff，并实际运行或复现关键验证（测试、命令、fixture），不得仅依据主代理的摘要裁决。
3. `docs/active-plans/` 下的过程文档（本文档、执行日志及其余计划文档）**不是**审查对象：审查者不得读取或引用它们，裁决只能基于代码、测试与上游计划文档。

## 3.2 裁决（四选一）

每个审查子代理必须给出**且仅给出**以下四种裁决之一：

| 裁决 | 定义 |
|---|---|
| **通过** | 审查者认为有**充分证据**支持当前的开发已经实现了门禁要求，且形成了**后续开发的可靠基础**。 |
| **投机通过** | 审查者认为实际工作内容**可以通过**门禁，但**不能充分排除**后续出现问题的风险。虽然如此，审查中获取的结果支持**后续开发风险可控**的判断。 |
| **补充内容** | 审查者认为实际工作内容**不足以通过**门禁、或后续有**较明显的风险**，但可以通过**简单的补充**改善到投机通过或者通过。此时审查者应当给出**内容补充要求**，并充分说明该补充要求与之前的计划（4 份上游文档与已验收的开发）的**兼容性**。 |
| **阻塞** | 审查者认为前面的开发有**明显的问题或重大风险项**，应当停止继续开发。 |

## 3.3 裁决汇总与流转

1. **审查通过标准：3 个审查子代理全部给出“通过”或“投机通过”，门禁才通过**，进入下一阶段（下一个 Phase / Gate）。
2. 裁决优先级：**阻塞 > 补充内容 > 投机通过 / 通过**。
   - 任一给出阻塞 → 门禁不通过，状态转为**阻塞**（§5）；
   - 无阻塞、但至少一个补充内容（即部分通过 / 投机通过 + 部分补充内容）→ 门禁暂不通过，进入“补充 + 重审”流程。
3. **补充后的对抗式重审**：
   - 主代理完成补充内容要求的补充工作（按 §4 计数）；
   - 补充完成后，主代理必须**重新拉起完整对抗式审查**：3 个全新独立审查子代理，重审**整个 Gate**（不是只审补充部分）；
   - **新的对抗式审查不能获知上一次审查内容**：重审 brief 不得包含任何上一轮审查意见、裁决、补充要求或说明；上一轮记录只保留在执行日志中，不得注入任何新审查者的 prompt；
   - 重审按 §3.1–§3.3 同样的规则裁决。
4. 主代理收到“补充内容”裁决后，必须先核对该补充要求与 4 份上游文档的兼容性；**补充要求与冻结语义冲突的，不得执行**，应记录证据并转为**阻塞**（§5）报告用户。
5. “投机通过”不阻塞门禁，但触发 §6 的风险记录义务。

---

# 4. 补充计数规则

1. 补充内容分为两类：
   - **实质性补充**：改变代码、测试、持久数据或配置，影响行为或门禁证据；
   - **文档性补充**：纯文档、注释、执行日志或 Agent Note 文本，不改变行为与门禁证据。
2. **纯文档性补充不计入次数**。
3. **实质性补充按 Gate 计数**：同一 Gate 累计 3 次实质性补充后，审查仍未全部“通过 / 投机通过”，状态转为**阻塞**（§5），待用户介入处理。
4. 任何一次“补充内容”裁决对应的补充工作（无论类别）完成后，都必须按 §3.3.3 重新拉起完整对抗式审查。

---

# 5. 阻塞语义

1. 触发阻塞的情形：
   - 任一审查子代理给出**阻塞**裁决；
   - 开发任务三次执行未完成且涉及门禁级语义（§2.3）；
   - 补充要求与冻结语义冲突（§3.3.4）；
   - 同一 Gate 3 次实质性补充后仍未全部“通过 / 投机通过”（§4.3）；
   - 发现与上游文档的语义冲突（按兼容性文档 §28 冲突处理规则：记录证据、停止对应任务、不跨 Gate）。
2. 进入阻塞后：
   - **停止一切后续开发**：不跨 Gate，不启动任何“可能先做通”的任务；
   - 在执行日志记录：Gate、触发原因、全部审查裁决与关键证据、重试 / 补充历史；
   - 输出简明的阻塞报告并等待用户介入；**用户未明确解除前，主代理不得自行重试该 Gate**。
3. 用户解除阻塞后，主代理按用户指示从该 Gate 继续（重新拉起完整审查周期），或按上游文档允许的范围内调整计划并记录到执行日志。

---

# 6. 投机通过风险台账

每个给出**投机通过**的 Gate，主代理必须把以下内容记入执行日志的风险台账（§7）：

```text
Gate 编号
风险点描述（源自审查者意见的提炼）
相关文件 / 任务 / 测试证据位置
当时判定“可控”的理由
```

风险台账**只追加**，供后续 bug 排查参考：主代理处理后续 bug 时，必须先对照相关 Gate 的风险台账再定位。

---

# 7. 执行日志

主代理在 `docs/active-plans/SESSION_ROUTER_LOG.md` 维护**只追加**的执行日志，至少记录：

1. 模型路由核验结果（执行启动时）；
2. 每个任务：任务号、执行次数（1–3）、结果、证据指针；
3. 每个 Gate：Gate 号、3 个审查者裁决与关键理由、汇总结果；
4. 投机通过风险台账（§6）；
5. 补充记录：Gate、类别（实质性 / 文档性）、实质性累计次数、内容摘要、兼容性说明；
6. 重审记录：轮次、已执行“不能获知上次审查内容”的确认；
7. 阻塞记录（如有）：触发原因与证据；
8. TODO 列表（§2 跳过的任务）及其关闭记录。

日志随每轮工作落盘提交，不得只保存在会话记忆中。

---

# 8. 无人值守执行纪律

1. 无人值守期间，主代理**不向用户发起中间确认**；用户介入仅发生在：
   - 阻塞（§5）；
   - 改变用户可观察语义的上游文档冲突（按兼容性文档冲突处理规则报告）；
   - 目标完成。
2. Gate 执行顺序按开发计划 §24：`G0 → G1 → G2 → G3 → G4 → G5 → G6/G7/G9（并行）→ G8 → G10 → G11 → G12`；任何 Gate 未通过，不进入下一个涉及其语义的 Phase（开发计划 §16）。
3. 每个 Gate 通过后提交并记录；commit 前缀按开发计划 §0.3。UI 中不依赖某 Gate 的纯 presentation 子任务可提前 mock，但不得 merge 为 production path（开发计划 §16）。
4. **完成判据**：G0–G12 全部通过、开发计划 §23 的 Definition of Done 满足，并产出最终交付总结。
